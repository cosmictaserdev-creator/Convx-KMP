### Playback reliability update (2026-10-25)

The desktop playback path now opens the proxied audio stream directly and uses full-file FFmpeg-to-WAV conversion only as a compatibility fallback. This removes the full-track download/transcode from normal startup and crossfade preparation. Playback stalls can trigger the same fallback once; startup and stall watchdogs report a bounded error instead of leaving an indefinite loading state. AndroidHost and iOS now preserve play/pause intent while resolving and buffering, share the toggle policy, and have startup watchdogs. Local playback policy tests, desktop compilation, and AndroidHost assembly pass. This is not yet an audible-playback proof: direct JavaFX stream playback and the iOS/AndroidHost guest playback flows still need runtime validation.

### Windows desktop playback — 2026-10-25

Guest InnerTube playback was exercised without signing in. The desktop BotGuard worker generated guest player and stream tokens, and Googlevideo served byte ranges beyond 3 MB. JavaFX Media rejects YouTube's fragmented AAC MP4 with `ERROR_MEDIA_INVALID`, so the desktop host now decodes the stream with FFmpeg to a temporary PCM WAV before opening it in JavaFX. Its byte-range proxy streams open-ended reads in bounded upstream chunks, and the decoder checks cancellation, applies a network read timeout, and deletes temporary audio when a deck is released. A Windows integration smoke run decoded a full 213-second, 3.4 MB AAC stream to a 37.5 MB WAV; JavaFX reached ready and advanced playback beyond one second. This confirms the guest stream, decoder, and JavaFX timeline path, but does not confirm sound on every output device. Crossfade and other platform behavior still need runtime exercise. FFmpeg's Windows native runtime adds about 25.5 MB; macOS/Linux classifiers are selected by the build but need packaging and runtime proof on their runners. Android-host and iOS still use the no-op PoToken provider and have not had guest playback verified. No account login was used. Desktop liquid-glass/backdrop rendering remains disabled after a prior Skiko stack overflow; opaque surfaces remain a known visual gap.

### Windows desktop crash investigation — 2026-10-25

Windows Application Error events recorded repeated `javaw.exe` exits with `0xc00000fd` (stack overflow); two faulted in `skiko-windows-x64.dll`. The minidumps do not contain a readable Kotlin/Compose call stack, so the exact drawing call is not proven. The desktop shell used the custom Capsule `ContinuousRoundedRectangle` shape on the sidebar, player, and queue surfaces. Those desktop-only uses now use Compose `RoundedCornerShape` to remove that native custom-shape path. A local `:desktopApp:compileKotlin` passed, then the desktop client launched and loaded guest Home and Explore without a new crash dump during the observation window. This is a launch/navigation smoke check, not proof that every interaction is crash-free; audio output remains unverified.

Repeated local debug launches left four separate Convx desktop windows running, each with its own playback engine. Desktop startup now takes a per-user file lock before creating the database or playback stack, so launches of this version cannot add more competing sessions. The four existing windows predate that guard and remain open; they need a normal app restart before the guard can own a session. The mini-player now reports `Preparing audio…` while FFmpeg decodes a full track and presents pause while buffering. The nested desktop build compiles with these changes; this pass did not launch another GUI window or verify speaker output.

A live guest track selection then reproduced the playback failure before audio startup: stream resolution returned `YouTube did not provide a complete, range-readable audio stream`. The resolver now keeps a progressive URL fallback when the range probe rejects a stream, and the desktop proxy forwards a complete upstream response when the source ignores `Range`. Range probes now use the same browser headers as the desktop proxy. Desktop and AndroidHost Kotlin compilation pass locally; progressive playback and iOS compilation/runtime still need validation.

The follow-up desktop change made JavaFX open that YouTube stream directly and transcode only after a media error or stall. That path was not proven against the known fragmented-AAC decoder failure and guest playback was reported unusable. Desktop startup now uses the previously exercised FFmpeg-to-WAV path again, with a 180-second bounded preparation window, cancellation and temporary-file cleanup. JavaFX only opens the completed local WAV; direct streaming remains available for silent crossfade preloading, where failure falls back to a normal decoded track start. The reverted path needs a fresh build/Actions run and Windows runtime smoke check with sound output.

KMP transition settings now route through one common playback planner on desktop, AndroidHost, and iOS. AutoMix is selectable in the desktop full player and reaches the planner instead of being rejected by the platform controller. Since the KMP hosts do not yet provide persisted audio analysis to this planner, AutoMix currently falls back to an ordinary crossfade for eligible tracks; the planner still declines some short or speech/live tracks. Beat matching, cue seeking, DJ filtering, and hardware audio behavior remain unverified. Common tests for disabled transitions, configured fade timing, no-analysis fallback, short-track policy, and AutoMix setting transitions pass; desktop and AndroidHost Kotlin compilation pass locally. iOS native compilation and runtime playback require macOS.

## Remaining Phase 0 decisions

These decisions do not need to block an isolated toolchain proof, but they must be assigned before the corresponding feature enters a shared implementation:

1. First-wave provider coverage and integrations on iOS and desktop, within the selected core music flows.
2. Local-library, removable-media, and network-share expectations on each target.
3. Listen Together support on iOS and desktop.
4. Desktop playback engine, codecs, outputs, and background behavior.
5. Target-specific audio-engine, DSP, hardware, and inference support for the included EQ/effects/analysis scope; report limitations explicitly.
6. New-client portable backup/import format and any transfer from Android schema 40.
7. Apple, Windows, and desktop distribution/signing account ownership.
